# v0.5.x Workflow Lifecycle — Improvement Plan

Carry-over from the v0.4.x workflow-lifecycle work (PRs #77–#88).  v0.4.x
unblocked the user journey with what was already wired (version history
dialog, `+ → From Template…` picker, FE+BE version display).  v0.5.x is
the **architectural shift** from "everything lives inside the DB and
moves through the UI" to "workflows are portable artifacts with their
own file format, discoverable through a real library surface."

This document is the **planning artifact**, not a spec.  Use it to scope
PRs; each item should land as one focused PR.

---

## 1. Backend snapshot-dedup for `workflow_version`

**Why:** PR #87 added a frontend guard that short-circuits `saveWorkflow`
when `hasChanges` is false, suppressing the no-op-click version-spam
case.  That covers ~95% of the problem in practice, but it's frontend-only
defence — a misbehaving / scripted / older client could still POST
`PUT /workflows/{id}` with `create_version: true` and an unchanged
snapshot, and the backend would happily append an identical row.

**What to ship:**

- In `crud.py` around the `if payload.create_version:` block
  (`app/api/v1/routes/workflows/crud.py:1053`), compute the new
  snapshot's `integrity_hash` and compare against the latest existing
  `WorkflowVersion` row's `integrity_hash`.  If identical, skip the
  insertion; return the existing version's id in the response so the
  client can update its UI.
- Update `WorkflowVersionListResponse` if needed so the client can tell
  "this save was a duplicate" from "we wrote a new row."
- Test: explicit unchanged-PUT-with-create-version-true asserts the
  version count does not increment.

**Why not in v0.4.x:** the frontend guard is the surgical fix; doing
both is belt-and-suspenders.  Worth the proper backend dedup in v0.5.x
once we also have file-import (which can create version rows on a
different path).

## 2. Canonical `.workflow.json` file format + round-trip

**Why:** the user's original ask — *"Save will actually save into a file
that + can load"* — is only half-met by v0.4.x.  Save persists to the
project DB; templates instantiate from bundled YAMLs; but nothing
exports a workflow definition as a portable file, and nothing imports
one.  Sharing a pipeline with a colleague still means screenshotting or
exporting Python.

**What to ship:**

- **Schema design.**  The YAML template shape under
  `src/spectra_sherpa/data/templates/*.yaml` is already canonical — the
  PR D smoke test (#84) pins its structural invariants.  Lift it into
  a single JSON schema (`spectra-sherpa.workflow/v1`) covering: nodes,
  edges, params, position, data_roles, certified_datasets (optional),
  metadata (created_by_frontend, created_by_backend, exported_at,
  source workflow_id if any).
- **Backend export.**  New `GET /workflows/{id}/export/definition` →
  application/json with the canonical schema.  Sibling to existing
  Python / Jupyter / Zip exports under the workflow's Export menu.
- **Backend import.**  New `POST /projects/{id}/workflows/import` →
  accepts the JSON, instantiates as a new sheet (mirror of
  `open-as-new-sheet` from #83).  Handles unknown node_type gracefully
  (4xx with a list of missing types), handles cross-project foreign
  refs (e.g. `data.source: experiment` IDs that don't exist on the
  importer's machine — degrade to "needs data binding").
- **Frontend.**  Export menu picks up a "Workflow definition (.workflow.json)"
  entry.  `+ ▾` menu picks up "Open workflow file…" with a native file
  picker.  Imported workflow lands as a new sheet in the current
  project.
- **Round-trip test.**  Export A → import → result B; structurally
  equal modulo IDs, positions, and timestamps.
- **Templates migrate.**  The bundled YAMLs should be loaded through
  the same schema validation so the import path is exercised by every
  shipped template.  No re-authoring needed if the schema is designed
  carefully here.

**Out of scope for the first cut:**

- Cross-instance secrets (API keys baked into a workflow's chat node).
  Strip on export; warn on import that they need to be re-entered.
- Embedded data (carrying experiment files inside the .workflow.json).
  Defer indefinitely — would balloon files; better to keep file/data
  references and require the importer to re-bind.

## 3. Workflow library surface — promote drawer to a real panel

**Why:** the current Project Details drawer (#83 added a Modified
column post-PR-E) is fine for ≤30 workflows per project.  Users with
more start drowning.  Search, filter, sort are minimum-table-stakes
for a "workflow library."

**What to ship (incremental):**

- Search box (name + description LIKE; cheap, no FTS index needed for
  v0.5.0).
- Filter chips: status (draft / shared / archived), type (
  classification / calibration / curve-resolution — inferred from
  node types, no schema change), modified-this-week / this-month.
- Multi-select rows for bulk archive / delete.
- Detail row preview (first 3 nodes, primary data source name) without
  having to open the workflow.
- Decide between: expand the drawer in-place, or break out into a full
  `/project/{id}/workflows` page.  Drawer is more contextual; page
  scales better.  My prior recommendation was the page; revisit during
  design.

**Out of scope for v0.5.0:**

- Cross-project workflow browsing.  Real architectural lift (new index,
  new route, new "scope" UI).  Wait for the user need.

## 4. Templates first-class

**Why:** v0.4.x ships 23 curated YAML templates loaded into DB on
startup.  Users can't currently create their own templates — only
duplicate an existing workflow.  Once the file format from §2 lands,
"save as template" is the natural pairing.

**What to ship:**

- `is_template: bool` column on `workflow` table (migration).
- `POST /workflows/{id}/save-as-template` action.  Strip data bindings
  (no experiment_id / file_id references in the template body), set
  `is_template = true`, exposed via `GET /workflow-templates`
  alongside the curated ones with a "yours" badge.
- "Save as template…" action in the workflow Actions menu.
- Template picker (#85's `TemplatePickerDialog.vue`) splits into two
  groups: **Curated** (existing 23) and **Your templates**.

**SCP-availability probe.**  v0.4.x's PR #87 mapped the SCP-missing
error string to a friendlier toast post-click.  v0.5.x should expose
`GET /system/extras` returning `{scp_installed: bool, …}` so the
template picker can disable SCP-backed templates *before* the click
(matching the disable pattern PR #88 introduced for needs-data
templates).

## 5. Version history polish

**Why:** PR #83 surfaced version history in a dialog with "open as new
sheet" (non-destructive).  Good baseline.  Two natural follow-ups
emerged from staging conversations:

- **Restore in place** — destructive sibling of "open as new sheet."
  Replaces the current workflow's content with the snapshot, behind a
  confirm.  The existing `POST /workflows/{id}/versions/{vid}/restore`
  endpoint already does this; just wire a second action button in
  `VersionHistoryDialog.vue` gated by a `<ConfirmDialog>` so users
  can't fat-finger it.
- **Diff view** — compare two snapshots node-by-node (added /
  removed / changed-params).  Real product surface; needs design.
  Defer until users actually ask.
- **Manual prune** — explicit "delete this version" affordance, since
  even with §1's snapshot-dedup, users may want to clean up old
  branches manually.  Behind a confirm.

**Per-version FE/BE software-version stamps** — explicitly *not* in
this list.  The v0.4.x discussion concluded those belong as a
**global app-version display** (which #82 shipped), not as
per-workflow_version columns.  Don't re-litigate.

## 6. Sheet/workflow UI cleanup

Backlog items from PR audits, none individually big enough to be its
own milestone but worth a sweep PR:

- **`resetDialogOpenedSheetUi` should also fire on tab-click.**  PR #88
  resets execution banner + inspector when opening from a dialog;
  switching tabs has the same stale-state leak but isn't yet wired.
- **Sheet-tab overflow.**  At ≥12 sheets the strip becomes horizontally
  scrollable (already works) but discoverability of distant sheets is
  poor.  Add an overflow `▾` button that opens a flat sheet list (with
  search if §3 lands first).
- **"Needs data" template UX.**  Currently the disabled "Needs data"
  button is the end of the line for templates that require explicit
  bindings.  Eventually those should open a binding picker dialog
  (project experiment + file per data role) — companion to the file-
  import flow.

## 7. App-version display improvements

`#82` shipped the footer + About dialog + drift indicator.  Worth a
small follow-up once we have one or two upgrade cycles under our
belt:

- **One-click hard-reload** button in the About dialog's drift
  warning, instead of the text-only instruction.
- **Extras status in About.**  After §4's `GET /system/extras` lands,
  surface `[scp]`-installed yes/no, model artifact count, plugin load
  status.  Turns the About dialog into a real diagnostics surface for
  support tickets.
- **GitHub link → release notes.**  Currently links to the OSS mirror
  homepage; could deep-link to `/releases/v{backend_version}` so users
  can find the changelog for the version they're running.

## Sequencing recommendation

If we ship in this order, each PR is independent and unlocks the
next:

1. **Backend snapshot-dedup** (§1) — small, contained, finishes the
   v0.4.x audit story properly.
2. **`.workflow.json` schema + export + import** (§2) — the
   architectural anchor of v0.5.x.  Everything else depends on the
   schema being right, so do this carefully and lock it once shipped.
3. **Workflow library panel** (§3) — needs nothing from §2 strictly,
   but ships better with file import as a complement.
4. **Templates first-class** (§4) — needs §2's file format.
5. **Version history polish + UI cleanup + About extras** (§5–§7) —
   parallelizable, any order.

---

## What this plan deliberately does NOT cover

- **Cross-project workflow moves** (other than via file export/import).
  Stays project-scoped per the v0.4.x principle.
- **Multi-user collaboration** (shared workflows, comments).  Belongs
  to the server/enterprise plane, not OSS.
- **Workflow templating language** (parameterized templates with
  variables).  YAMLs today are parametric only at the data-source
  layer; a richer templating system is a v0.6.x conversation.
- **AI-assisted workflow construction**.  Already exists at some level
  (`POST /workflows/{id}/ai-fork`); v0.5.x doesn't change it.
